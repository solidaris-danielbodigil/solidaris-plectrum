# Contribute

Everything ships through this repository: tokens, stylesheets, components, and this Storybook. Develop in Storybook first; applications only ever install versioned packages (packed tarballs today, the registry after the first release) — never source paths.

Related pages:

- [Writing stories](?path=/docs/docs-writing-stories--docs) — CSF, attached MDX, Storybook MCP
- [AI strategy](?path=/docs/docs-ai-strategy--docs) — contracts, index, Storybook MCP tools
- [CSS architecture](?path=/docs/docs-css-architecture--docs) — ITCSS layers and BEMIT mixes

Anyone can contribute — developers and designers, in the core team or in an application team. Every change starts the same way: a **proposal to the core design-system team**, not a scaffold. The core team answers within the triage below; nobody waits for the core team to build.

## Three answers to a proposal

Application teams migrating to Plectrum need variants the system does not have yet. That is expected. What is not acceptable is a variant landing in `libs/ui` as if it were core, or living in an application with no trace here. Triage sorts every proposal into one row:

<DocsTable
  headers={['Core team says', 'Where it lands', 'Owner', 'Badge']}
  rows={[
    ['It already exists — PrimeNG, a Core component, a token', 'Nowhere new. Use it; the docs page gets the missing example if that is why you missed it', 'Design-system team', 'Core'],
    ['System-level — a second application will need it, or it is a variant of a Core component', 'libs/ui / libs/styles / the UI Kit Component collection, through the normal pull request and design-system review', 'Design-system team', 'Core'],
    ['App-specific — only your screens need it', 'Your application layer: Patterns/{App} in Storybook, owner: <app> in the metadata, tokens in 01-settings/_settings.{feature}.scss', 'Application team', 'Candidate or App-specific'],
  ]}
/>

Running Storybook locally is never the drift risk — nothing leaves a branch without a pull request and the CI gates. The risk is building before the decision, or a code-owned token teaching Figma after the fact. Both are what the Propose and Review steps exist for.

## Status and owner

Every component docs page opens with two badges from its `.metadata.ts` `governance` block (CSS-only blocks declare them in their stories file). The index at `.ai/contracts/index.json` carries the same two fields, so agents and audits read one source.

<DocsTable
  headers={['Status', 'Meaning', 'Who may import it', 'What changes it']}
  rows={[
    ['Core', 'Generic, owned by the design-system team. Filed under Custom components or Shell', 'Every application', 'Deprecation, by the core team'],
    ['Candidate', 'Built for one application and flagged for promotion. Filed under Patterns/{App}', 'The owning application; others ask the core team first', 'Promotion to Core, or settling as App-specific'],
    ['App-specific', 'Owned by one application for its own screens. Documented here, not part of the design-system contract', 'The owning application only', 'A second application needing it — which reopens the proposal'],
    ['Deprecated', 'Scheduled for removal; the note names the replacement or the reason', 'Nobody new', 'Removal in a later release, after usages migrated'],
  ]}
/>

The **owner** badge names the accountable team: `design-system`, `ishare` or `icrm`. Ownership and status travel together — a Core component is always design-system owned; a Candidate or App-specific component never is.

## Promotion

Promotion is a move, done by the core team when a proposal comes back with the system-level answer for something an application already built:

1. Generic name and API — application vocabulary leaves the inputs and the BEM block.
2. Tokens move from the `proposals/{app}` Figma collection into Component or Semantic, and from `_settings.{feature}.scss` into the shared settings files.
3. The Storybook title moves from `Patterns/{App}` to `Custom components` or `Shell`; `governance` becomes `status: 'core'`, `owner: 'design-system'`.
4. A changeset records the bump and the release workflow publishes the packages; the application bumps, deletes its local copy and imports from `@solidaris/ui`.

Until step 3 the component stays the application's, whatever `libs/` folder it sits in.

## Audit outcome

The live table is [Component status](?path=/docs/docs-component-status--docs) — it reads `.ai/contracts/index.json`. Decisions from the September 2026 catalogue audit:

- Core stays generic: List, Profile Card, Profile Drawer, Copyable Text, Form Field, Empty State, Icon, Avatar, Input Clear, Detail List, Drawer, Accordion, Timeline, Skeleton Slot, Toolbar, and the navigation shells.
- Delay Prediction Card and Transactions CICS Modal stay App-specific (iSHARE).
- CSS-only blocks (Accordion bordered, Timeline content-only) stay documented on their own pages, not in the Angular index.

## Set up

```bash
git clone <repo> && cd solidaris-nx
npm install
npm run storybook     # http://localhost:6006
```

Node **20.19+, 22.12+ or 24** — the range Angular 21 supports. CI (`ci.yml`) runs every gate on Node 20; the GitHub Pages deploy (`deploy-ishare-pages.yml`) builds on Node 24, so both ends of the range are exercised. The apps run with `npm start` (iSHARE) and `npm run start:icrm`.

## Create a component

Only after the core team's decision. Then:

```bash
npm run pds:component -- --owner=design-system   # core team: status core
npm run pds:component -- --owner=ishare          # application team: status candidate
```

The scaffolder asks for name, category, type and optional PrimeNG wrap, then creates the Angular files, the `.metadata.ts` contract with its `governance` block, a stories stub, the `_components.{name}.scss` partial (forwarded from the core barrel), and regenerates `.ai/contracts/index.json`. Then:

1. Check **PrimeNG MCP**, **Figma MCP**, then **Storybook MCP** (`docs-list`) when `npm run storybook` is up — reuse before inventing ([CSS architecture](?path=/docs/docs-css-architecture--docs) has the authoring order; [AI strategy](?path=/docs/docs-ai-strategy--docs#storybook-mcp) has the MCP tools).
2. Missing tokens go to `01-settings` first, cited with their Figma variable. Application teams alias semantic roles only.
3. Layout is `o-flex` / `o-layout` classes in the template — never flex/gap CSS in `06-components`.
4. One story per state; the component is not done without them ([Writing stories](?path=/docs/docs-writing-stories--docs)). Agents use `docs-show` and `get-storybook-story-instructions` before writing CSF. Application-owned pages are titled `Patterns/{App}/…`.

By default the **agents do this work** — ask the Plectrum coordinator for a component and it runs research, tokens, implementation and QA end to end ([AI strategy](?path=/docs/docs-ai-strategy--docs)). Every command stays runnable by hand. The agent does not skip the proposal either: it asks for the owner and files an open question when the decision is missing.

## Language

User-facing copy in `libs/ui` lives in a colocated `{name}.i18n.ts` (`fr` + `nl`). Components resolve it with `injectPdsMessages()` from the `PDS_LOCALE` token. The token factory reads Angular `LOCALE_ID` (`nl*` → `nl`, otherwise `fr`); apps can also call `providePdsLocale('nl')`. String inputs still win when the host passes them.

This Storybook has a **FR / NL** toolbar (`globals.locale`). One `Dutch` story per migrated component pins `globals: { locale: 'nl' }` and asserts a Dutch string. Terminology decisions live in `.ai/questions/nl-copy-review.md`.

**Not a gate yet:** `npm run lint` (`ng lint`) has no architect target and no ESLint configuration, so no lint step runs in CI. Style and token hygiene are enforced by `tokens:lint` and `tokens:check-prefix` above.

Review rules the gates do not encode — one developer review, the design-system review under `libs/`, the token risk levels — live in `.ai/rules/07-version-control.md` and `.ai/contracts/protocols/token-audit.md`.

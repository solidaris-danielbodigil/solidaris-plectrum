# Contribute

Core tokens, stylesheets, components and this Storybook ship through this repository. Application teams build approved candidates in their own repositories and submit metadata, commit provenance and preview evidence through a reviewed central PR. Applications install versioned packages — packed tarballs of the current version until npm publish is on — never source paths.

## A small correction

A typo, a broken example or a wrong link is a pull request on this repository. You do not open a proposal for that.

A missing component, variant or token is a [proposal](https://github.com/solidaris-danielbodigil/solidaris-plectrum/issues/new?template=proposal.yml). Say what the screen must do, which components you tried, and attach a Figma link. The core team answers within two working days: use what exists, they will build it, or your team builds it and owns it. That response time is provisional until the team confirms it.

Anyone can contribute — developers and designers, in the core team or in an application team. Every change starts the same way: check the catalogue, then a **proposal to the core design-system team**, not a scaffold. Open a [proposal issue](https://github.com/solidaris-danielbodigil/solidaris-plectrum/issues/new?template=proposal.yml). The core team answers within the triage below; nobody waits for the core team to build.

## Three answers to a proposal

Application teams migrating to Plectrum need variants the system does not have yet. That is expected. What is not acceptable is a variant landing in `libs/ui` as if it were core, or living in an application with no trace here. Triage sorts every proposal into one row:

<DocsTable
  headers={['Core team says', 'Where it lands', 'Owner', 'Badge']}
  rows={[
    ['It already exists — PrimeNG, a Core component, a token', 'Nowhere new. Use it; the docs page gets the missing example if that is why you missed it', 'Design-system team', 'Core'],
    ['System-level — a second application will need it, or it is a variant of a Core component', 'libs/ui / libs/styles / the UI Kit Component collection, through the normal pull request and design-system review', 'Design-system team', 'Core'],
    ['App-specific — only your screens need it', 'The application team builds and owns it in its repository, with local stories and approved token aliases. A submitted Candidate gets a central listing linked to that team’s preview; promotion is a separate Core decision', 'Application team', 'Candidate or App-specific'],
  ]}
/>

Running Storybook locally is never the drift risk — nothing leaves a branch without a pull request and the CI gates. The risk is building before the decision, or a code-owned token teaching Figma after the fact. Both are what the Propose and Review steps exist for.

## Already built it?

If an application team already designed or coded something without a proposal, open the [same issue](https://github.com/solidaris-danielbodigil/solidaris-plectrum/issues/new?template=proposal.yml) and attach what exists. The core team still decides — rewrite onto PrimeNG or Core, keep it App-specific, or promote later. It does not land as Core and it is not added to a core backlog by default.

## Promotion

Promotion is a move, done by the core team when a proposal comes back with the system-level answer for something an application already built:

1. Generic name and API — application vocabulary leaves the inputs and the BEM block.
2. Tokens move from the `proposals/{app}` Figma collection into Component or Semantic, and from `_settings.{feature}.scss` into the shared settings files.
3. The integrated stories appear under `Custom components` or `Shell` in central Storybook; `governance` becomes `status: 'core'`, `owner: 'design-system'` while the stable component ID is retained.
4. The Figma component is designed from the repo on the branch — an agent via Figma MCP, or a designer by hand. Bind variables; do not paint hex from a screenshot. Merge and publish stay human.
5. A changeset records the bump. After the publication pipeline is enabled and a verified release exists, the application upgrades, deletes its local copy and imports from `@solidaris/ui`.

Until step 3 the component stays the application's, whatever `libs/` folder it sits in. Token writes use the Plugin API: agent + Figma MCP when a session is running, Plectrum tokens plugin otherwise ([Figma sync](?path=/docs/docs-token-pipeline-figma-sync--docs)).

## Set up

In an **application repository**, install the runtime packages and `@solidaris/plectrum-devkit` as described in [Build with Plectrum](?path=/docs/get-started-use-plectrum-in-an-app--docs#initialize-the-team-toolkit). Run `plectrum init` once, then `plectrum catalogue` and `plectrum doctor`. Open a proposal issue; the Core team records its decision in `.ai/candidates/proposals/<application>-<slug>.json`. After that record is merged with `approved-candidate`, run `plectrum scaffold --name <slug> --proposal <application>-<slug>`. Complete the metadata JSON, story, style and evidence, then run `plectrum check --profile ci` and commit. Publish an HTTPS preview and CI result for the exact commit. With `GH_TOKEN` or `GITHUB_TOKEN`, run `plectrum candidate-submit --name <slug> --proposal <application>-<slug> --preview <url> --checks <url>` to open a central intake PR. Repeating this after a new commit revises the stable ID; `plectrum candidate-withdraw --id <application>-<slug> --reason <text>` opens a withdrawal PR. The central JSON submission appears in Find a component with a link to the team's preview after review and merge. `plectrum update` refreshes editor adapters when the installed toolkit changes. Local `index.json` files are never submitted.

The commands below apply to contributors working **inside the Plectrum repository**:

```bash
git clone https://github.com/solidaris-danielbodigil/solidaris-plectrum.git
cd solidaris-plectrum
npm install
npm run storybook     # http://localhost:6006
```

Node **20.19+, 22.12+ or 24** — the configured range. CI (`ci.yml`) currently runs on Node 24. The apps run with `npm start` (iSHARE) and `npm run start:icrm`.

## Create a component

Only after the core team's decision on a [proposal issue](https://github.com/solidaris-danielbodigil/solidaris-plectrum/issues/new?template=proposal.yml). Then:

```bash
npm run pds:component -- --owner=design-system   # core team: status core
npm run pds:component -- --owner=ishare          # local demo candidate in Plectrum
```

The scaffolder asks for name, category, type and optional PrimeNG wrap, then creates the Angular files, the `.metadata.ts` contract with its `governance` block, a stories stub, the `_components.{name}.scss` partial (forwarded from the core barrel), and regenerates `.ai/contracts/index.json`. Then:

1. Check **PrimeNG MCP**, **Figma MCP**, then **Storybook MCP** (`docs-list`) when `npm run storybook` is up — reuse before inventing ([CSS architecture](?path=/docs/docs-css-architecture--docs) has the authoring order; [AI strategy](?path=/docs/docs-ai-strategy--docs#storybook-mcp) has the MCP tools).
2. Missing tokens go to `01-settings` first, cited with their Figma variable. Application teams alias semantic roles only.
3. Layout is `o-flex` / `o-layout` classes in the template — never flex/gap CSS in `06-components`.
4. One story per state; the component is not done without them ([Writing stories](?path=/docs/docs-writing-stories--docs)). Agents use `docs-show` and `get-storybook-story-instructions` before writing CSF. Application-owned pages are titled `Patterns/{App}/…`.

## Language

User-facing copy in `libs/ui` lives in a colocated `{name}.i18n.ts` (`fr` + `nl`). Components resolve it with `injectPdsMessages()` from the `PDS_LOCALE` token. The token factory reads Angular `LOCALE_ID` (`nl*` → `nl`, otherwise `fr`); apps can also call `providePdsLocale('nl')`. String inputs still win when the host passes them.

This Storybook has a **FR / NL** toolbar (`globals.locale`). One `Dutch` story per migrated component pins `globals: { locale: 'nl' }` and asserts a Dutch string. Terminology decisions live in `.ai/questions/nl-copy-review.md`.

## Before you commit

`npm install` installs a git hook. It runs `npm run check:commit` before the commit is created. That run checks docs, contracts, token prefix, token usage, style lint, and that the generated index, changelog and token files are already saved. Fix the failure, stage any regenerated file, and commit again.

`git commit --no-verify` skips this hook. A pull request into `main` still runs the full CI gates below. A push of a feature branch by itself does not.

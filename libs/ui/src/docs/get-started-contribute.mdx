# Contribute

Anyone can contribute — developers and designers, in the core team or in an application team. A typo, a broken example or a wrong link is a pull request on the Plectrum repository. A missing component, variant or token is a [proposal](https://github.com/solidaris-danielbodigil/solidaris-plectrum/issues/new?template=proposal.yml): say what the screen must do, which components you tried, and attach a Figma link.

Components can start in an application repository **or** with the design team in Figma. Candidate designs belong in **PLECTRUM · Custom components**; **Plectrum DS · PrimeNG v21** contains the PrimeNG design and all token variables. A design review in Figma approves a design direction; Core still reviews the implementation and a verified release before an Angular component is available to applications.

## Develop and submit a candidate

**Current workflow:** the candidate scaffolder still requires Core's merged approval. The planned autonomy model will separate local development from the decision to share a component through Core; it is not implemented yet. Track that dependency explicitly in the application epic — see [Planned onboarding](?path=/docs/get-started-use-plectrum-in-an-app--docs#planned-onboarding).

For an `approved-candidate` decision, in the **application repository** with the initialized toolkit ([Build with Plectrum](?path=/docs/get-started-use-plectrum-in-an-app--docs#initialize-the-team-toolkit)). Commit the candidate, publish an HTTPS preview and a CI result for that exact commit, then submit. Submitting again after a new commit revises the same stable ID. The reviewed central JSON — never a local `index.json` — makes the candidate appear in [Find a component](?path=/docs/start-here-catalogue--docs) with a link to your preview.

Before scaffolding, prepare the application's [Storybook and executable tests](?path=/docs/get-started-use-plectrum-in-an-app--docs#set-up-storybook-and-tests). Align `paths.candidateStyles` with the local ITCSS component layer and wire its imports. The current generator creates a story, metadata JSON, SCSS and an evidence checklist; it does not configure Storybook, generate a unit spec or register the SCSS import. The toolkit's CI profile validates those files and static contracts, but does not execute the tests recorded as evidence.

## Contribute to Plectrum Core

### Start from a reviewed Figma design

A designer can open the same central proposal using a Custom components node as the source. Record the original design, the reviewed version, the design-team decision and the intended owner. Core checks for an existing PrimeNG or Plectrum solution and records its implementation decision. No application repository or `candidate-submit` is required for this route.

<Unstyled>
  <Story of={Figures.DesignOrigin} />
</Unstyled>

Keep the Custom components branch, review, merge and publication links with the proposal. If new tokens are needed, review them in a separate PrimeNG 21 token branch and return them through the token sync. Core implements the approved component in this repository and publishes it through the normal release pipeline. [Profile header](https://www.figma.com/design/IRkr21rHS0w7rI0bgrv1fZ/PLECTRUM-%C2%B7-Custom-components?node-id=2438-10587) is a design-origin example following a design-team review of Profile Card. It is not yet an installable replacement; the old Profile Card remains deprecated and exported.

### Work in the Plectrum checkout

Corrections and Core-owned work happen in a **Plectrum checkout**, through a reviewed pull request:

## Promote existing work

Promotion is a Core decision about an accepted candidate. The core team integrates and generalizes it, a designer completes the Figma work, and a verified release ships it. The application then upgrades, deletes its local copy and imports the released component. Until integration the component remains the application's.

## Status and owner

Every metadata-backed Plectrum component page opens with two badges from its `.metadata.ts` `governance` block. The central index carries the same two fields, so agents and audits read one source.

<DocsTable
  headers={['Status', 'Meaning', 'Who may import it', 'What changes it']}
  rows={Object.values(STATUS_PRESENTATION).map((status) => [status.label, status.hint.replaceAll('{owner}', 'the owning team'), status.importers, status.changedBy])}
/>

The **owner** is a team ID from the shared registry below — the only values metadata, the scaffolder and candidate records accept. For a new application, ask Core to add the real team, application and repository URL to `.ai/contracts/registry.json` before running `plectrum init`. Local demo entries do not represent external adoption.

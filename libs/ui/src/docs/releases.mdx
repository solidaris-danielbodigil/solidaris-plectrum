# Releases and versioning

Changesets versions the three runtime packages together. Applications install a verified GitHub Packages release or the packed tarballs for an unpublished revision. Package manifests and What's new describe source versions; the release manifest proves publication.

The historical `2.0.1-devkit-0.2.0` release used four public package names. <span>{REGISTRY_PUBLISHED ? 'This verified release uses the private pds-* package names.' : 'The new pds-* names shown here are the private distribution target; use their authenticated install commands only after their first verified release.'}</span> A protected manual release uses a separate classic package PAT and checks GitHub's actual visibility for each package before publishing a matching Storybook.

## Process

1. A change lands with a **changeset** (`npm run changeset`) describing the bump (patch / minor / major) and the affected packages.
2. On merge to `main`, the release workflow (`.github/workflows/release.yml`, `changesets/action`) opens or updates the **version PR** — `chore(release): version packages` — accumulating pending changesets into version bumps and changelogs.
3. CI packs the four artifacts, builds an isolated consumer and checks package ownership, registry target and tarball integrity with `npm run release:check`. The attended release workflow checks the same commit, publishes exact archives, tests a fresh registry installation, and records the release manifest and Storybook bundle.
4. Application repositories receive the bump as a Renovate / Dependabot pull request (`tools/consumers/renovate.json`).

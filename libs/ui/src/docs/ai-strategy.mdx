# AI strategy

Agents work from **typed contracts** instead of reading the whole repository. We call this Contract-Driven Development (CDD): a typed metadata schema, a generated component index and short protocols. People still review, and own Storybook, CSS and Figma library publication. Agents may propose token variables on a PrimeNG 21 branch and components on a Custom components branch; without an agent, use the Plectrum tokens plugin for token writes.

## Team repositories

<p>Application teams install <code>{PACKAGE_NAMES.ui}</code>, <code>{PACKAGE_NAMES.plectrum}</code> and <code>{PACKAGE_NAMES.styles}</code> for code and styles, and <code>{PACKAGE_NAMES.toolkit}</code> for the CLI, rules and process {processContract.version}. On installation, the starter runs <code>plectrum bootstrap</code>, which adds <code>.ai</code> rules, skills and agents, Cursor and VS Code/Copilot adapters and MCP configuration. After an upgrade, run <code>{command('consumerUpdate')}</code>: it refreshes these files and reports any you edited instead of overwriting them.</p>

Because application teams own their components, the Plectrum agent acts as their first reviewer: before anything is built, it checks PrimeNG and the catalogue, suggests what to reuse or compose, answers layout and UX questions, and says when a designer should decide. For new UX it still recommends showing the work early to the core team or a designer. Application agents use the `plectrum` CLI and your local paths; the Core agents described below work only in the Plectrum repository. MCP configuration points to a server, it does not start one. Setup: [Build with Plectrum](?path=/docs/get-started-use-plectrum-in-an-app--docs).

## Storybook MCP

<p>While <code>{processContract.capabilities.storybookMcp.requires}</code> runs, <code>@storybook/addon-mcp</code> serves <code>{processContract.capabilities.storybookMcp.endpoint}</code>, registered in Cursor and VS Code. {processContract.capabilities.storybookMcp.note} The gate is <code>{processContract.capabilities.storybookMcp.gate}</code>.</p>

MCP is the live catalogue: stories, Controls and docs pages. When Storybook is not running, agents use `index.json`, the offline map of paths, BEM blocks, relationships, status and owner.

### Create a component

Pre-flight is PrimeNG MCP → Figma MCP → `index.json` → `docs-list` (when Storybook is up) → `pds:component`. After the stub exists, `docs-show` a sibling (Copyable Text, Form Field) and copy that CSF + MDX shape. Gate with `contracts:check`, `docs:check`, `test-storybook`.

### Create stories

1. `docs-show` the component — do not add a Control that is missing from `.metadata.ts` `props`.
2. `get-storybook-story-instructions`, then apply [Writing stories](?path=/docs/docs-writing-stories--docs): colocated CSF, required states, `play` from `story-tests.ts`.
3. `stories-preview` the new canvases.
4. `test-run` for quick local feedback, then `npm run test-storybook` — the gate CI runs.

### Subagents

The Plectrum agent coordinates component work. Select **Plectrum** in the Cursor or VS Code/Copilot agent picker (or type `/plectrum` in Cursor), then describe the component, the proposal and the owner. It calls the specialist roles when needed. Example in the Plectrum repository:

```
/plectrum Add a Core status banner.
Owner: design-system.
Figma: [UI Kit link].
Proposal: [issue link].
Use PrimeNG Message if it already covers this.
```

<p>In an application, the agent creates local components with <code>{command('consumerScaffold')}</code>, without waiting for Core. In the Plectrum repository, it uses <code>{command('scaffold')}</code>.</p>

Prompt templates for tokens, Figma and stories are in [`.ai/contracts/protocols/ai-prompts.md`](https://github.com/solidaris-danielbodigil/solidaris-plectrum/blob/main/.ai/contracts/protocols/ai-prompts.md).

## Reference

### Metadata file

Every `libs/ui` component has `{name}.metadata.ts` next to the class. Shape: `ComponentMetadata` inferred from `.ai/contracts/schema/component.schema.ts`. It is also the single source of truth for the component's docs page — the MDX embeds figures that render these blocks (`pds-docs-status`, `pds-docs-contract`); see [Writing stories → Documentation source](?path=/docs/docs-writing-stories--docs#documentation-source). `npm run docs:check` fails a page that restates a block by hand.

Import the type from the workspace alias `@solidaris/contracts` and export a metadata const (`EmptyStateMetadata`, …). The generated Storybook registration reads these consts; the Angular runtime entry exports component APIs, not metadata.

### Index

`npm run contracts:generate` scans colocated metadata and package exports, then generates `.ai/contracts/index.json`, Storybook registration and the toolkit's offline catalogue and schemas. CI checks those artifacts for drift. Application agents read the snapshot installed with their toolkit version. The Plectrum checkout can expose Storybook MCP while its local Storybook runs; an application does not assume `localhost:6006` points to Plectrum.

### Scaffold

```bash
npm run pds:component     # scaffold in the Plectrum checkout
npm run contracts:generate # refresh inventory, registration and toolkit snapshot
```

`pds:component` creates the Angular files, a story and colocated metadata in the Plectrum checkout; generation registers the metadata and exports. In an application, use `plectrum scaffold` under the configured candidate paths and keep the contribution local until reviewed.

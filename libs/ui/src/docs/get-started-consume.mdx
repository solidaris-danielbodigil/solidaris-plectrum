# Build with Plectrum

This is the application team's path from package access to a themed Angular screen, local Storybook and executable checks. The source starter in `tools/consumers/starter` targets devkit <code>{DISTRIBUTED_PACKAGES.find((pkg) => pkg.role === 'toolkit')?.version}</code>. It must be released before it can be installed from the private registry. For an earlier published version, use that release's versioned documentation and manual setup.

<Unstyled><Story of={Figures.InstallFlow} /></Unstyled>

## Prerequisites

**Step 1 · Application team.** Create a repository from the source starter, or connect an existing Angular application. An empty directory has no `package.json`, so npm cannot discover dependencies or run the project's `postinstall`. Set `plectrum.team`, `plectrum.application` and `plectrum.repository` in the manifest before installation. Local IDs permit local work; Core registration is required before central intake.

- Use a supported Node version ({workspacePackage.engines.node} for this checkout) and ensure access to the {REGISTRY.operations.visibility} packages in {REGISTRY.operations.registry}.
- Supply registry credentials on the developer machine and in CI. The starter `.npmrc` selects a registry but contains no secret.
- For an existing application, preserve its build, stories and hooks. Review config conflicts before attaching the bootstrap.

## Install the packages

**Step 2 · Application root.** Run `npm install` in the copied starter. Its manifest declares Angular, PrimeNG, `@primeuix/themes`, the three runtime packages, Sass, Storybook, test tools and the devkit. Runtime packages must use one compatible version; the toolkit has its own version.

<DocsTable headers={['Package', 'Contents', 'Install as']} rows={DISTRIBUTED_PACKAGES.map((pkg) => [pkg.name, pkg.description, pkg.role === 'runtime' ? 'Application dependency' : 'Development dependency'])} />

<Unstyled><Story of={Figures.Install} /></Unstyled>

The application's `postinstall` invokes `plectrum bootstrap`. It does not install more dependencies. If npm scripts are disabled, run `npm run pds:bootstrap` afterward. Commit generated configuration and the lockfile. Repeated installation preserves application files; CI verifies that the setup was committed instead of rewriting it.

## Initialize the team toolkit

**Step 3 · Inspect what installation generated.** Bootstrap creates `.plectrum/config.json`, managed editor adapters, `.ai` rules, skills, protocols and agents, MCP configuration, a local Git hook and a GitHub Actions workflow. It also configures Angular's stylesheet, Storybook and unit-test targets. `plectrum update` refreshes managed files after a devkit upgrade and reports conflicts rather than overwriting team edits.

<Unstyled><Story of={Figures.Initialize} /></Unstyled>

Check identity, selected Angular project and source paths in `.plectrum/config.json`. Set the project explicitly for a multi-project workspace. Local team instructions belong outside managed adapters. Figma and Storybook MCP endpoints are optional and distinct from the local Storybook server.

## Wire the stylesheet

**Step 4 · Already wired by bootstrap for the starter.** Eight empty local ITCSS layer entries live under `src/styles/`. `src/styles.scss` interleaves each shared `pds-styles` layer with the matching local layer; Angular and Storybook load that entry once. The starter declares Sass, so no package named `scss` is needed.

```text
src/styles/
  01-settings/_index.scss
  02-tools/_index.scss
  03-generic/_index.scss
  04-elements/_index.scss
  05-objects/_index.scss
  06-components/_index.scss
  07-utilities/_index.scss
  08-trumps/_index.scss
```

Keep local layers free of copied shared tokens. <code>{command('consumerScaffold')}</code> writes `_components.<slug>.scss` in `06-components` and registers its import. The devkit supplies Agenda font assets and configures `/assets/fonts/agenda`; the starter installs `bootstrap-icons`. Open Sans remains an approved application font-source decision. Bootstrap reports an existing full Plectrum stylesheet import as a conflict to avoid duplicate CSS.

## Boot the theme

**Step 5 · Provided in the starter.** `src/app/app.config.ts` calls `providePlectrum()` and the animation provider. The local Storybook preview uses the same theme provider. In an existing application, merge these providers with its router and other providers.

## First component

**Step 6 · Verify the runtime.** Run `npm start`; the starter PrimeNG button should render with the Plectrum theme. Then import a Core component in an application screen. This Form Field example checks the UI package, PrimeNG directive and theme together:

```ts
import { Component } from '@angular/core';
import { InputText } from 'primeng/inputtext';
import { FormFieldComponent } from '@solidaris-danielbodigil/pds-ui';

@Component({
  selector: 'app-root',
  imports: [FormFieldComponent, InputText],
  template: `
    <pds-form-field
      label="Member number"
      inputId="member"
      hint="Ten digits, no spaces"
      requiredLabel="obligatoire"
    >
      <input pInputText id="member" type="text" autocomplete="off" />
    </pds-form-field>
  `,
})
export class App {}
```

[Form Field](?path=/docs/custom-components-form-field--docs) has the component contract; [Find a component](?path=/docs/start-here-catalogue--docs) lists other shared exports.

## Set up Storybook and tests

**Step 7 · Run the generated tools.** `npm run pds:storybook` opens local Storybook with an example story, controls, docs and the accessibility addon. `npm run pds:build-storybook` builds a static preview; `npm run pds:test:unit` runs Angular unit tests and `npm run pds:test:stories` executes Storybook play and accessibility checks in Chromium. Install the browser once locally with `npx playwright install chromium`; generated CI installs it before testing. New local components receive a story and a unit spec from the scaffold. Complete their assertions and manual accessibility evidence before delivery.

The central Storybook remains the published shared-component reference. The generated story test runs interactions and automated accessibility checks; the evidence checklist still records manual checks and their limits. Preview hosting, private access and visual regression service remain application and CI decisions.

## Validate

**Step 8 · Run the portable checks.** `npm run pds:check:ci` verifies installed package compatibility, tokens, managed files, candidate metadata/API alignment, stories, unit specs, ITCSS imports and completed evidence. It does not compile the application or execute tests. Run `npm run build`, `npm run pds:test:unit`, `npm run pds:build-storybook` and `npm run pds:test:stories` as separate gates. Generated GitHub Actions runs these gates and passes `GITHUB_TOKEN` to npm; grant the application repository read access to the private packages first. Merge protection and alignment with Solidaris global CI must be configured with CI owners.

## Workspace readiness

**Step 9 · Reproduce from a clean clone.** Confirm that package access works in CI, generated files and lockfile are committed, the app and Storybook render the theme and fonts, unit tests and static build run, and the CI owner has mapped these commands to required Solidaris jobs. An existing application may need a targeted integration instead of a second Angular project.

Update runtime packages together, upgrade to a compatible toolkit, run `plectrum update` and the checks above. <Unstyled><Story of={Figures.Upgrade} /></Unstyled> [What's new](?path=/docs/docs-what-s-new--docs) describes migrations.

## Before you invent

Search PrimeNG and the shared catalogue first. If the gap is application-specific, the team may create and maintain a local component immediately. Core approval is required for shared intake, not local implementation.

<Unstyled><Story of={Figures.BeforeYouInvent} /></Unstyled>

Use published `var(--pds-*)` tokens, BEMIT classes and local ITCSS layers. [Find a token](?path=/docs/foundations-token-finder--docs) helps choose a token.

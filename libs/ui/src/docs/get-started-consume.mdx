# Build with Plectrum

Use this guide in your **application repository**. It takes you from package access to a themed screen, then identifies the tooling and checks needed before the team starts delivering components.

**Installing the packages does not yet create a complete application workspace.** The current toolkit initializes Plectrum configuration, editor instructions and a checks workflow. Angular setup, local ITCSS folders, Storybook, test runners and a pre-commit hook still need application setup. The target is a starter where one installation prepares that environment; see [the planned onboarding work](#planned-onboarding).

Follow these steps in order. Each step states where to work and how to check the result:

## Prerequisites

**Step 1 · Application team, with Core for package access and registration.** Start from a working Angular application or your team's approved Angular starter. The current devkit does not create Angular projects or install their build tools.

**Check before continuing:** the application builds on its own, the developer can read the private packages, and Core has supplied the actual team/application IDs. An existing iShare demo inside Plectrum does not register the new front-end repository automatically.

**Review the paths** in `.plectrum/config.json` against your actual workspace. A multi-project repository may not keep its sources under `src`. The toolkit must scan the real application sources and styles.

In Cursor, select the generated **Plectrum** agent; in VS Code, select **Plectrum** in the chat agent picker. Agent use is optional: developers run the same CLI commands by hand.

**Rules, skills and protocols:** the installed devkit contains the application rules, role instructions, catalogue and schemas. It also carries central rules/skills/protocols as reference material. `init` does not copy the full `.ai/` directory or automatically activate every skill in your editor. Central paths such as `libs/ui` and central npm scripts do not exist in your application. Keep team-specific instructions outside generated files.

Set Figma or Storybook MCP URLs in `.plectrum/config.json` when needed. A Storybook documentation URL is not an MCP endpoint; configuring MCP does not install Storybook or grant access to Figma.

**Check:** the configuration contains your repository and paths, catalogue lookup works, and the diagnostic succeeds. No Angular providers, SCSS imports, local ITCSS skeleton, Storybook configuration, unit test runner or pre-commit hook have been installed by this step.

## Wire the stylesheet

**Step 4 · Application build configuration and global styles.** `pds-styles` supplies SCSS source. Configure a compatible Sass-capable Angular builder; there is no separate package named `scss` to install. If your chosen tooling needs a direct Sass dependency, declare it in the application.

In the application's build options in `angular.json`, include `src/styles.scss` in `styles` and resolve the shared ITCSS source from the package:

<pre><code>{`"stylePreprocessorOptions": {
  "includePaths": ["node_modules/${PACKAGE_NAMES.styles}/src"]
}`}</code></pre>

For the initial screen using shared styles only, `src/styles.scss` loads the packaged system:

```scss
@use '01-settings/settings.prefix' as *;
@use 'main';
```

Here `main` resolves to the **package's** entry point. If you later add a local `styles/main.scss`, make the two imports unambiguous and avoid importing the shared CSS twice.

### Local ITCSS structure

The team should follow the same ITCSS/BEMIT architecture for its own styles. The shared layers stay in the package; local layers hold application extensions. This skeleton is **not generated by the current init command**:

```text
src/styles/
  01-settings/_index.scss
  02-tools/_index.scss
  03-generic/_index.scss
  04-elements/_index.scss
  05-objects/_index.scss
  06-components/_index.scss
  07-utilities/_index.scss
  08-trumps/_index.scss
  main.scss
```

Keep the layer entry points empty until needed; do not copy shared token values or component styles into them. Put new application component styles in `06-components/_components.name.scss` and import each partial once through the layer entry point. Use the same global entry point in Angular and local Storybook.

**Agree the layer composition before adding local styles.** Loading all local components after the complete shared stylesheet can place them after utilities that should take precedence. Configure and verify the shared/local order with Core using [CSS architecture](?path=/docs/docs-css-architecture--docs). Automated composition and generator placement are part of the planned starter.

The current candidate generator uses the configured `paths.candidateStyles`; it does not automatically create or wire this ITCSS skeleton. Align that path with your chosen component layer before generating candidates, then add their imports. The generator's current workflow is described in [Contribute](?path=/docs/get-started-contribute--docs).

### Fonts, icons and browsers

Agenda is currently supplied in the Plectrum repository at `libs/assets/fonts/agenda`, rather than in the style package. Obtain those four `.woff2` files from Core, place them in the application's assets and configure asset copying so `/assets/fonts/agenda/*.woff2` resolves. This asset transfer is a separate onboarding task today.

Open Sans is not bundled. Load it through your team's approved font source. Install `bootstrap-icons` and add `node_modules/bootstrap-icons/font/bootstrap-icons.css` to the application's global `styles` list. Include the same assets in local Storybook.

Agree the application's browser support with the team and verify it against the Angular version in use.

**Check:** the application compiles SCSS, token custom properties and shared classes are present in the browser, and fonts/icons load without missing-file errors. For local styles, verify a component and a utility together to check the cascade.

## Boot the theme

**Step 5 · `src/app/app.config.ts`, or the equivalent application provider configuration.** Add these providers to the existing configuration; preserve routing and other application providers.

<pre><code>{`// src/app/app.config.ts
import { ApplicationConfig, provideZoneChangeDetection } from '@angular/core';
import { provideAnimationsAsync } from '@angular/platform-browser/animations/async';
import { providePlectrum } from '${PACKAGE_NAMES.plectrum}';

export const appConfig: ApplicationConfig = {
  providers: [
    provideZoneChangeDetection({ eventCoalescing: true }),
    provideAnimationsAsync(),
    providePlectrum(),
  ],
};`}</code></pre>

`providePlectrum()` registers the PrimeNG theme and emits every `--p-*` custom property. The generated `--pds-*` tokens fall back to literals, so styles render even before the theme boots — but PrimeNG components need the provider.

The Storybook **Preset** control (`v1` / `v0.6`) switches this catalogue's theme; it is not the package version. `providePlectrum()` defaults to preset v1. Use the same provider setup in the application's Storybook. For older preset migrations, see [What's new](?path=/docs/docs-what-s-new--docs).

**Check:** a PrimeNG control renders with the Plectrum theme and the application starts without provider errors.

## First component

**Step 6 · An application screen or temporary smoke-test screen.** Render a Core component around a PrimeNG input to check package imports, theme and shared styles together:

```ts
// src/app/app.ts
import { Component } from '@angular/core';
import { InputText } from 'primeng/inputtext';
import { FormFieldComponent } from '@solidaris-danielbodigil/pds-ui';

@Component({
  selector: 'app-root',
  imports: [FormFieldComponent, InputText],
  template: `
    <pds-form-field
      label="Member number"
      inputId="member"
      hint="Ten digits, no spaces"
      requiredLabel="obligatoire"
    >
      <input pInputText id="member" type="text" autocomplete="off" />
    </pds-form-field>
  `,
})
export class App {}
```

`ng serve` shows a labelled, themed field: the label and hint come from `pds-form-field` ([Form Field](?path=/docs/custom-components-form-field--docs)), the input chrome from the Plectrum preset. Every Core Angular component is exported from the UI package root — the component's docs page names the class to import.

PrimeNG components use the Plectrum preset as-is ([theme gallery](?path=/docs/primeng-actions--docs)). [Find a component](?path=/docs/start-here-catalogue--docs) lists each Core component. Layout with `o-flex` / `o-layout`, chrome with `u-*`, values via `var(--pds-*)`.

**Check:** the example builds and renders, its label targets the input, and the hint, spacing and theme are visible. A successful screen proves the runtime integration; it does not prove that local tests and CI are ready.

## Set up Storybook and tests

**Step 7 · Application development tooling.** Each team needs its own Storybook for local components and patterns. The central Storybook documents the shared packages; it does not execute your application's stories.

**The current devkit does not install Storybook, its builder/addons or test runners.** A generated `.stories.ts` file needs a configured Storybook to run. Create a tooling task in the onboarding epic and agree the supported setup with Core:

1. Declare compatible Storybook/Angular and test dependencies in the application, preserving existing tooling.
2. Configure local story discovery, the Plectrum providers, the global stylesheet and static assets.
3. Add server, static build and headless test scripts to the application's `package.json`.
4. Render the first example in a story and add an assertion covering its behavior.
5. Configure unit tests and automated accessibility checks; document keyboard and screen-reader checks that remain manual.
6. Produce a preview accessible to the reviewers, with a reference to the commit tested.

The authoring conventions in [Writing stories](?path=/docs/docs-writing-stories--docs) apply, but its central repository paths and helper imports are not a portable application configuration. Do not copy the central Storybook folder unchanged.

**Check:** start the local catalogue, build it, then run a unit test, a story interaction and an accessibility check. Deliberately break an assertion to confirm the runner fails. A story file, an empty suite or a completed evidence checklist is not proof that tests ran.

`plectrum init` creates `.github/workflows/plectrum-checks.yml`. That workflow installs dependencies and runs the toolkit profile, whether an agent or a person made the change. It does not add the application build, unit tests, Storybook tests, visual tests or Solidaris-specific quality gates.

On pushes to `main`, the generated workflow also invokes the adoption submission command. Reporting is disabled by default; enable it only when the team wants to submit reports and has configured the required `PLECTRUM_ADOPTION_TOKEN` secret. See [Report adoption](#report-adoption).

For GitHub Actions, grant the application repository access to the private packages, set the required package-read permissions and configure npm registry authentication for the installation step. The generated workflow does not supply package credentials. Configure dependency-bot access separately as required by the organisation.

With the Solidaris CI owners, map the toolkit commands to the existing pipeline and add the build/test steps from the preceding section. Record which jobs block merging, their reports and who fixes failures. If a different CI provider is used, run the same CLI there; the generated GitHub workflow does not configure that provider. Keep managed-file changes compatible with `plectrum update`, which reports edited generated files as conflicts.

**Pre-commit:** the current devkit does not install a hook in the application. Agree a fast local profile and connect it to the team's existing hook mechanism. Repeat required checks in CI; skipping a local hook must not bypass them. The central `check:commit` script assumes the Plectrum checkout and is not an application hook to copy.

**Check:** a clean CI installation succeeds with the repository's own credentials; Plectrum checks, the application build and executable tests run; a known failing check prevents the expected merge. The global Solidaris requirements still need confirmation with their owners.

## Workspace readiness

**Step 9 · Application team review before closing the onboarding work.** Track these as acceptance criteria in the iShare epic, with an owner and evidence for each:

- Packages install from the private registry on a developer machine and in CI.
- Application identity and scan paths are correct; toolkit diagnostics and checks pass.
- The first screen renders with the shared theme, styles, fonts and icons.
- Local ITCSS placement and imports are configured and verified; component styles are loaded once.
- Local Storybook starts and builds using the same providers, stylesheet and assets as the application.
- Unit, story-interaction and accessibility tests execute and demonstrate that failures are detected.
- The pre-commit checks and required CI jobs are connected to the team's workflow.
- Editor instructions resolve the installed toolkit; team-specific instructions are preserved.
- A second developer can reproduce the setup from the committed manifest, lockfile and configuration.

A green toolkit check alone does not complete this list. These are the development conditions to establish before treating the application as equipped to the same quality standard as Core.

## Planned onboarding

The agreed target is a Plectrum application starter where `npm install` installs compatible dependencies and initializes the missing structure: empty ITCSS layers, SCSS wiring, theme, local Storybook, executable tests, hooks, CI configuration and application instructions. The component generator will place each style in `06-components`, add its import and update its metadata. Repeat installations will preserve application code.

Local component development should become independent of the Core mutualisation decision. **That autonomy and the complete starter are planned work, not capabilities supplied by the current toolkit.** Today the candidate generator still requires an approved proposal. Until the changes are delivered, use the current contribution procedure and track the missing onboarding capabilities explicitly.

Track the starter, portable quality tools and autonomy changes as explicit onboarding work. Use the installed release's documentation when checking which parts have shipped; a development-preview page is not evidence of package publication.

After onboarding, reporting is a separate, optional activity; it is not required to render a screen or run local checks.

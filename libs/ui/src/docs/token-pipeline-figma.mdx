# Figma sync

Two Figma files, two jobs: [Plectrum DS · PrimeNG v21](https://www.figma.com/design/wjMnb8GsK8bVKA7UreOJ4L/Plectrum-DS--PrimeNG-v21-) holds PrimeNG and every token variable; [PLECTRUM · Custom components](https://www.figma.com/design/IRkr21rHS0w7rI0bgrv1fZ/PLECTRUM-%C2%B7-Custom-components) holds Plectrum components and candidates. Tokens sync with the PrimeNG 21 file only.

Figma sends variables to the repository through a staging branch; the repository sends proposed tokens back to a PrimeNG 21 branch. Designers merge both ways by hand. See also the [pipeline overview](?path=/docs/docs-token-pipeline--docs) and the [script reference](?path=/docs/docs-token-pipeline--docs#commands).

### Repository responsibilities

1. Plugin commits land on `design-tokens/sync`. `Plectrum_v1/ts` is never overwritten in place.
2. `.github/workflows/tokens-sync.yml` runs `tokens:build`, then `tokens:audit` (blocking) and `tokens:validate-preset` (theme gate only).
3. `tokens:report` summarises the sync: changed values, check results and next steps. The summary becomes the pull request body and, once merged, the [Sync status](?path=/docs/docs-token-pipeline-sync-status--docs) page.
4. `tokens:notify-figma` posts the same summary as a comment in the PrimeNG 21 file (`FIGMA_TOKEN` with `file_comments:write`; `FIGMA_SYNC_COMMENT_NODE_ID` pins it to a frame). Without the secret, the step is skipped.
5. The workflow opens a pull request that promotes staging → `libs/plectrum/src/tokens.json` when the audit passed.
6. Theme files are copied into `Plectrum_v1/` only if `tokens:validate-preset` passes. Code-owned gaps listed in `audit-allowlist.json` warn instead of failing.
7. Manual fixes stay in `Plectrum_v1/ts/extend.ts`.

## One token file

Figma variables can only alias variables **in the same file**. A separate token file per application would break aliases such as `ishare/card/bg → surface/50`, so tokens proposed by an application go in a **per-application collection** inside PrimeNG 21. Components still live in Custom components.

Consequences:

- Aliasing between application tokens and Primitive / Semantic tokens works without a publish–subscribe hop.
- Each application has its own namespace.
- Promoting a token to the design system is a move between collections.
- Collections stay well below Figma's limits (5 000 variables, 40 modes).

Figma remains the source of truth for primitives and semantics. Component tokens are code-owned and proposed to Figma when they have no Figma node.

## Repository → Figma

When a shared token starts in code (a missing surface step, a feature colour), run `tokens:propose` to write `proposed.dtcg.json`, then apply the selected tokens on the PrimeNG 21 branch `proposals/{app}`. Tokens that stay local to one application are not proposed.

When Core integrates a candidate, its Figma design goes on a separate Custom components branch, bound to published PrimeNG 21 variables. See [Contribute](?path=/docs/get-started-contribute--docs#start-from-a-reviewed-figma-design).

## Package distribution

Applications install the code, styles and Agenda font files as published packages, so each application's `package.json` shows which design-system version it uses. See [Build with Plectrum](?path=/docs/get-started-use-plectrum-in-an-app--docs#wire-the-stylesheet).

- Changesets version the three libraries together on merge. The registry is abstracted through `publishConfig` and `.npmrc.example`.
- `npm run pack:smoke` packs the tarballs, installs them into a throwaway Angular application without path aliases, and builds it.
- Application repositories can adopt the Renovate configuration in `tools/consumers/renovate.json` (or equivalent Dependabot configuration) so design-system bumps arrive as pull requests. Run the installed toolkit's `plectrum check --profile ci` in their CI; the central `tokens:lint` command belongs to the Plectrum repository.
- Storybook has two modes: source (`npm run storybook`) and packed `dist/` in CI (`npm run build-storybook:packed`).

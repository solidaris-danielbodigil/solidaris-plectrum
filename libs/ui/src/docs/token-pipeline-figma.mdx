# Figma sync

Two one-way transports connect the Plectrum UI Kit and the repository. One is live; the other is built and parked.

- **Figma → repository** — live. The PrimeUI theme generator plugin syncs variables to a staging branch. A workflow promotes them through a pull request.
- **Repository → Figma** — parked. Code-owned tokens are proposed for a Figma branch; the automated write needs Figma's Enterprise-only Variables API. See [Status](#status).

Neither transport writes the main Figma file automatically. Agents operate the repository side of both — see [Agents](#agents). See the [pipeline overview](?path=/docs/docs-token-pipeline--docs) for the full architecture, [Commands](?path=/docs/docs-token-pipeline--docs#commands) for script flags, and the [CSS-first surface](?path=/docs/docs-token-pipeline-css-first-surface--docs) for how applications consume the output.

### Repository responsibilities

1. Plugin commits land on `design-tokens/sync`. `Plectrum_v1/ts` is never overwritten in place.
2. `.github/workflows/tokens-sync.yml` runs `tokens:build`, then `tokens:audit` (blocking) and `tokens:validate-preset` (theme gate only).
3. `tokens:report` summarises the sync — changed values against the current `tokens.json`, check results, what happens next. It is written to the Actions job summary, becomes the pull request body, and is committed as `sync-report.generated.ts` so the [Sync status](?path=/docs/docs-token-pipeline-sync-status--docs) page shows it to everyone without GitHub access once the pull request merges.
4. `tokens:notify-figma` posts the same summary as a comment thread in the Plectrum UI Kit (`FIGMA_TOKEN` with `file_comments:write`; optional `FIGMA_SYNC_COMMENT_NODE_ID` pins the thread to a frame). Promoted and blocked syncs both reach the designer in Figma. Without the secret the step skips itself; it never blocks the promotion.
5. The workflow opens a pull request that promotes staging → `libs/plectrum/src/tokens.json` when the audit passed.
6. Theme files are copied into `Plectrum_v1/` only if `tokens:validate-preset` passes. Code-owned gaps listed in `audit-allowlist.json` warn instead of failing.
7. Manual fixes stay in `Plectrum_v1/ts/extend.ts`.

The first sync confirmed the plugin's shape (`aura/*` sets, quoted numeric names, composite shadows, hex8 colours); see `tools/tokens/PLUGIN_SETUP.md`.

## Single Figma file

Figma variables can only alias variables **in the same file**, and the REST API cannot update remote variables. A separate file per application would break aliases such as `ishare/card/bg → surface/50`. Application-proposed tokens therefore land in a **per-application collection** inside the shared UI Kit.

Consequences:

- Aliasing between application tokens and Primitive / Semantic tokens works without a publish–subscribe hop.
- Each application has its own namespace.
- Promoting a token to the design system is a move between collections.
- Collections stay well below Figma's limits (5 000 variables, 40 modes).

Figma remains the source of truth for primitives and semantics. Component tokens are code-owned and proposed to Figma when they have no Figma node.

## Agents

Agents run the repository side of both transports. They read the UI Kit through the Figma MCP and do not write to it: no agent holds a Variables scope, and the outbound write is parked ([Status](#status)). Plugin sync, branch review, merge and publish stay with the designer. Roles and the component prompts: [AI strategy](?path=/docs/docs-ai-strategy--docs#prompts).

### Prompts

Cursor: start the message with `/Solidaris`, or write "Use the Solidaris subagent to …". VS Code: select **Solidaris** in the chat agent picker. Templates with placeholders: `.ai/contracts/protocols/ai-prompts.md`, Prompt E; Prompt A and B are the review and translation prompts the examples refer to.

#### Token from a Figma decision

```text
/Solidaris Translate the Figma decision at {figma-node-url} into --pds-* tokens.
Use Prompt B from .ai/contracts/protocols/ai-prompts.md. For each value: the Figma
variable, the closest existing --pds-* token or MISSING, primitive or semantic, the
01-settings file, and the --p-* bridge when a PrimeNG component is involved.
Propose first; write nothing until I confirm.
```

#### Promotion pull request review

```text
/Solidaris Review the token promotion pull request #{number}
(design-tokens/sync → libs/plectrum/src/tokens.json).
Use Prompt A. Compare the sync report with the diff, classify each changed token,
and flag renamed or removed variables that a component consumes (tokens.consumed
in the .metadata.ts files). Recommendation: Accept, Accept with small changes,
Revise before merge, or Reject.
```

#### Drift check

```text
/Solidaris Run the Token Auditor on libs/styles/src/01-settings.
Prefix compliance, semantic coverage, PrimeNG sync, and Figma drift against the
Primitive and Semantic collections of the Plectrum UI Kit. Report only; no fixes.
```

#### Code-owned token proposal

```text
/Solidaris iSHARE needs a surface step between surface/50 and surface/100 for the
dossier list rows.
Declare --pds-color-surface-75 in 01-settings with a comment naming the intended
Figma variable (color/surface/75), use it in
libs/styles/src/06-components/_components.list.scss, and run
npm run tokens:propose. Give me the proposed.dtcg.json entry the designer enters
on the branch proposals/ishare. Do not run tokens:apply.
```

- Changesets version the three libraries together on merge. The registry is abstracted through `publishConfig` and `.npmrc.example`.
- `npm run pack:smoke` packs the tarballs, installs them into a throwaway Angular application without path aliases, and builds it.
- Application repositories copy `tools/consumers/renovate.json` or `dependabot.yml` so design-system bumps arrive as pull requests, and run `pds-tokens-lint` so hard-coded hex/px values and unknown `--pds-*` names fail their CI.
- Storybook has two modes: source (`npm run storybook`) and packed `dist/` in CI (`npm run build-storybook:packed`).

# Use the Plectrum agent

> **In short.** For application teams. Ask `/plectrum` before you build anything: it checks what already exists, helps with layout, tokens and states, and builds local components with you. It answers from the Plectrum version you installed, without network access. Core still decides what is shared.

## Start it

`npm install` sets it up. In **Cursor**, pick **Plectrum** in the agent picker or type `/plectrum`. In **VS Code / Copilot**, pick **Plectrum** in the chat agent picker. Describe what the screen must do, not the component you think you need.

The agent calls specialist roles when a task needs them: UX Researcher, UX Engineer, Frontend Dev, Tester, Token Auditor and Architect.

## What it does not replace

- **Designers.** The agent names the decisions a designer should take. Show new UX early to the core team or a designer, while you build. It is advice, not an approval step.
- **Core decisions.** Sharing a component with other teams needs a Core decision. The agent prepares the proposal; Core decides.
- **Checks and review.** Checks, tests and pull-request review run the same way whether a person or the agent wrote the code.

## What is measured

Plectrum measures whether the agent helps, without reading what you ask it.

- **Usage.** Each call to the `plectrum` server and each `plectrum` command adds one line to `.plectrum/telemetry`: the tool name, the component ID and the outcome. Never the request, the code or file names. The folder is ignored by git. Set `telemetry.enabled` to `false` in `.plectrum/config.json` to turn it off.
- **Effect.** When the agent helped with a commit, it adds a trailer to the message: `Plectrum-Agent: reuse=<component ids>`, `scaffold=<slug>` or `advice`.
- **Sharing.** The usage report counts both over the last 30 days and sends the totals to Core with the component usage, only when usage reporting is on.

Core reads only these totals, per application, on the <a href={`${DASHBOARD_URL}#/design-system/agent`}>Plectrum dashboard</a>. Searches with no match point to gaps in the catalogue, and similar local components in several applications point to components worth sharing. Nothing in the totals identifies a person.

### Search quality

Requests written the way teams ask are replayed against the catalogue in the Plectrum repository each time a component or its documentation changes, and the agent may never find less than it did before; nothing in your application's build depends on this check, or on how you use the agent. The results are on the <a href={`${DASHBOARD_URL}#/design-system/search`}>Plectrum dashboard</a>.

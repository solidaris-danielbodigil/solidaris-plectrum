# Validation d'une application Plectrum externe — 30 septembre 2026

Le parcours « Build with Plectrum » a été exécuté dans une application Angular copiée du starter vers un répertoire temporaire **hors du monorepo**. Les quatre packages ont été construits et installés comme archives npm (`pds-ui`, `pds-plectrum` et `pds-styles` en 2.0.2 ; `pds-devkit` en 0.4.0), sans alias TypeScript vers les sources du dépôt. Le test reproductible est `npm run pack:smoke`.

`npm install` sans `--legacy-peer-deps` a réussi et a déclenché le `postinstall` de l'application. Un premier essai a révélé que les plages `^21.2.16` du starter pouvaient résoudre des patchs Angular incompatibles entre `@angular/core` et `@angular/compiler` ; le starter fixe désormais les versions Angular à un ensemble cohérent. Le bootstrap a créé les huit couches ITCSS locales sous `src/styles/`, intercalées une fois chacune avec la couche partagée correspondante. `npm run pds:component -- --name smoke-card` a créé le partial dans `src/styles/06-components` et l'a importé une fois dans son `_index.scss`, sans SCSS colocalisé.

La même application a validé le build Angular, les polices Agenda dans les artefacts Angular et Storybook, les tests unitaires, le build Storybook et deux tests de stories. Son index Storybook contient les pages Docs de l'exemple Plectrum et du composant généré. Le devkit a généré les règles et skills `.ai`, les agents Cursor et VS Code/Copilot, le hook pré-commit, la CI et les contrats. `plectrum check --profile ci` a passé après complétion des métadonnées et preuves du composant ; les cas incomplets ou incohérents ont bien échoué. Le test a également exercé la mise à jour sans écraser les notes d'équipe, l'export de candidature et le rapport d'adoption local.

Cette validation prouve le contenu des **archives construites depuis cette branche** et le parcours du starter. Elle ne prouve pas que ces versions sont publiées dans GitHub Packages ou disponibles depuis le Nexus Solidaris. Elle ne vérifie pas non plus l'authentification, le certificat du poste de Maxence, la configuration de la CI globale Solidaris ni un clone propre du futur dépôt iShare. Le `.npmrc` du starter pointe actuellement le scope Plectrum vers GitHub Packages ; le routage vers Nexus suppose que DevOps y rende d'abord les quatre packages accessibles.

Pour le pilote iShare sur l'infrastructure d'entreprise, faire confirmer par DevOps l'URL de registre réellement utilisée, la disponibilité des quatre packages, les droits de lecture et la chaîne de certificats validée par Node sur les postes et en CI. Puis créer un dépôt iShare depuis le starter de la **version publiée correspondante**, suivre les neuf étapes de Storybook et reproduire les commandes de build, Storybook, tests et `pds:check:ci` depuis un clone propre. Ne pas désactiver la vérification TLS pour contourner `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`.

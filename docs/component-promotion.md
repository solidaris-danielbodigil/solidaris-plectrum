# Promoting an application candidate

The stable identity is `<team>:<component>` and the candidate record ID is `<application>-<component>`. A team candidate stays in the application repository until a reviewed Core integration actually adds its implementation to Plectrum. See the [central record contract](../.ai/candidates/README.md) and Storybook → Start here / Contribute.

1. The team opens a proposal issue. Core records the decision and owner in `.ai/candidates/proposals/<id>.json` via `npm run candidate:record -- proposal --team TEAM --application APP --component SLUG --issue URL --decision approved-candidate --decided-by @REVIEWER --decision-url URL --note TEXT` and merges it. The team scaffolds only after `approved-candidate` is merged.
2. The team builds the candidate locally, fills metadata, stories and evidence, and runs the installed toolkit's `plectrum check --profile ci`. It commits the source and publishes preview and CI URLs for the same commit.
3. `plectrum candidate-submit` sends the metadata and provenance as a JSON pull request to this repository. Subsequent commits use `revise`; `candidate-withdraw` reserves the ID and removes the listing. The team's `index.json` is not submitted.
4. Core reviews the pinned source commit, preview, metadata, package versions and accessibility evidence, then records acceptance/rejection through `npm run candidate:record -- review --id APP-SLUG --decision accepted --pull-request URL --reviewed-by @REVIEWER --note TEXT` in a reviewed PR. The reviewer record references the current source revision.
5. For promotion, Core imports and adapts the **actual implementation**: generic naming/API, dependencies, FR/NL i18n, tests, stories, styles and approved tokens. The Figma design and token references are reconciled. The central `.metadata.ts` uses the same component ID with `status: 'core'`, `owner: 'design-system'` and a package-eligible distribution. A changeset records the release impact.
6. Core records `.ai/candidates/promotions/<id>.json` with `npm run candidate:record -- promotion --id APP-SLUG --integration-pr URL --api URL --tokens URL --dependencies URL --i18n URL --accessibility URL --figma URL`, then runs `npm run contracts:generate`, `npm run candidate:check`, `npm run contracts:check`, `npm run docs:check` and the relevant builds/tests. Generated `index.json` and exports come from central source. The promotion record preserves the link from application candidate to Core ID.
7. In an attended Figma session, the designer creates or updates the candidate on a verified `proposals/{app}` branch of **PLECTRUM · Custom components**. Any new or changed variables go through a separate `proposals/{app}` branch of **Plectrum DS · PrimeNG v21**, where all tokens live. Bind the component to the published variables; never copy token values into the component file as a new token source. Record the component branch and node. When tokens change, also record the token branch, mapping, pinned proposal revision and reviewed return-export PR. Design approval, each branch merge and library publication remain human decisions. Core records `.ai/candidates/figma-returns/<id>.json` with `npm run candidate:record -- figma-return --file record.json` only after the required evidence exists; see [candidate records](../.ai/candidates/README.md).
8. After a verified package release, the application upgrades its packages, deletes its local candidate and imports the Core component. Publication is part of P7; a merged integration PR alone is not a released package.

## When the component starts in Figma

Designers can propose a component or a redesign directly in **PLECTRUM · Custom components**. Open a central proposal with the source node, the revised design node, its intended use and the design-team review outcome. Core records its own decision after checking the PrimeNG catalogue, existing Plectrum components, accessibility and implementation feasibility. This route does **not** require an application repository, `plectrum candidate-submit`, or a fabricated application candidate record.

After approval, retain the Custom components branch/node URL, design review, merge and publication evidence. If the design needs new variables, propose and review them separately in PrimeNG v21 and sync them into the repository through the token pipeline. Core then implements the component in Plectrum with metadata, stories, tests, exports and a changeset; a verified release is needed before teams can import it. The proposed Figma design is not itself a released Angular component.

**Profile header** follows this design-origin route: the earlier Profile Card design was reviewed with the design team and evolved into [Profile header](https://www.figma.com/design/IRkr21rHS0w7rI0bgrv1fZ/PLECTRUM-%C2%B7-Custom-components?node-id=2438-10587). Record the review decision and publication evidence before closing the design gate. The existing `plectrum:profile-card` stays deprecated and exported until a separately reviewed replacement has a stable ID and verified release. iSHARE is outside this change.

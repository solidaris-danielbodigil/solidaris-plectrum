# Pipeline recovery and evidence

Use this guide after a pipeline stage fails. The source contracts are `.ai/contracts/registry.json`, `process.json`, `compatibility.json`, the component metadata, and the reviewed candidate/adoption records. The installed toolkit carries a versioned snapshot of those contracts. A generated `index.json` is an output of central generation, never an application submission.

Keep the failing run/PR URL, source commit and package versions in the incident record. Correct the source or input, rerun the relevant check and leave the stage visibly incomplete until its review and external evidence exist. Do not edit generated files as a shortcut.

| Symptom | Inspect | Recovery and completion evidence |
| --- | --- | --- |
| Candidate rejected or absent from Find a component | Proposal decision and revision in `.ai/candidates/proposals/`, submission JSON and `candidate:check` output | Merge an `approved-candidate` decision before scaffolding. Run `plectrum check --profile ci`, capture preview and CI URLs for the submitted commit, and rerun `candidate-submit` to revise the same stable ID. A Core reviewer merges the reviewed record; `contracts:generate -- --check` then proves the central index is current. A draft or unmerged PR is not a candidate acceptance. |
| Candidate or report has incompatible versions | Toolkit `doctor` and `check --profile ci`, installed package manifests and `.ai/contracts/compatibility.json` | Upgrade the runtime packages and toolkit as a compatible set, run `plectrum update` and `plectrum check --profile ci`, then regenerate the record. Keep the rejected record for diagnosis; do not change its version fields to bypass compatibility checks. |
| Adoption missing or stale | `.plectrum/config.json` reporting switch, application registry entry, `.ai/adoption/<application>.json`, source revision and observation time | Register the real external application, grant the reporting identity repository access, opt in with `reporting.enabled`, then run `plectrum adoption-report` and `plectrum adoption-submit`. Review and merge the report PR. A later report replaces older observations; no report means unknown adoption, not zero usage. Keep `reportIngestionEnabled` false until a real external report passes review. |
| Managed agent files conflict during upgrade | `plectrum update` conflict output, installed process version and local notes | Save team notes in unmanaged files. Resolve the managed-file conflict against the newly generated adapter, preserving team notes separately, then rerun `plectrum update`, `doctor` and `check --profile ci`. Do not copy the central `.ai` tree or treat a hand-edited managed file as a new source of truth. |
| Review cannot complete | PR review requests, `.github/CODEOWNERS`, `registry.json` Core reviewer and alternate, branch protection | Request review from a configured independent Code Owner with access. The PR author cannot approve their own PR. Keep branch protection and checks; escalate reviewer access/ownership to the repository owner rather than bypassing the gate. |
| Figma inbound export or token audit fails | `tokens-sync.yml` job and `sync-report`, `libs/plectrum/sync/tokens.json`, `tokens:audit`, preset validation | Correct the source in the verified Figma library or staged export, rerun the plugin export to `design-tokens/sync`, then review the generated `tokens/promote-staging` PR and report. Do not hand-edit generated SCSS/TS. Reject an invalid preset; a successful export alone does not imply design approval or library publication. |
| Repo-to-Figma candidate stalls | Candidate review/promotion records, branch key and node URLs in the proposed Figma return | Resume on the verified `proposals/{app}` branch with the attended agent or plugin. Apply only reviewed token mappings, bind variables, record node/review/merge/publication URLs and run the inbound return checks. Leave the Figma-return record absent until all required human decisions and return evidence exist. |
| Package publication fails or stops partway | `publish-release.yml` run, exact `main` SHA, package API visibility, integrity and `release.json` | Fix the underlying permission/visibility/build error, then rerun the **same** release ID on the **same** source revision. Matching archives are reused; a changed archive or published release with missing assets needs maintainer investigation. Never overwrite an immutable package or unpublish an installed version; deprecate and prepare a patch when needed. |
| Docs deployment fails or latest points to an older release | Pages run, GitHub Release assets, `release.json`, `contracts.json`, archive hashes | Retry Pages assembly after fixing the failing source/run. The previous deployed site and `storybook/latest/` stay in place on failure. To roll back a bad development preview, revert its source commit and deploy the resulting green build; for a bad published package, publish a corrective version and retain the immutable archived Storybook. |

## Acceptance evidence before handoff

Record a real external repository and its package read identity, a reviewed proposal/submission and adoption PR, the Figma proposal branch and approved candidate, the inbound token PR, the exact release run, four private package pages, versioned Storybook and Pages `latest` pointer. Link the PRs and immutable run URLs in the [P9 acceptance record](p9-acceptance.md). Local smoke tests establish portability but do not prove live GitHub/Figma authorization or review.

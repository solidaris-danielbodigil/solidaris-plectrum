# Storybook content migration ledger

Draft — 9 September 2026. Companion to `.cursor/plans/plectrum-storybook-audit-and-agent-plan.md` §3 (B04).

Decision rule: **content a consumer needs to implement or use a component stays beside the example in Storybook; content that explains how to own or operate the system moves to the customer knowledge base.** Code, tests, schemas, generated manifests and executable commands stay in the repository; the knowledge base explains and links, it does not mirror them.

Status values: `keep` · `split` · `move` · `retired`. `Target` and `Owner` are **unresolved** until the customer names the destination space and the receiving team — do not invent URLs or people.

Story ids are from the live Storybook `index.json`; incoming links were collected with `rg '\?path=/docs/' libs/ui/src`.

## Drift prevention

- One authoritative home per fact. API, types and defaults stay tied to source (`.metadata.ts`, generated docs tables). Executable commands stay in `package.json` / workflows.
- The knowledge base links to a repository revision, not to a hand-copied table. Never mirror `tokens.generated.ts`, `index.json`, `changelog.generated.ts` or live token inventories.
- Each migrated page records: content owner, last reviewed date, package/build version. A generation timestamp is not human review evidence.
- zeroheight design guidance already exists; map its role next to the knowledge base instead of adding a third copy of design principles.
